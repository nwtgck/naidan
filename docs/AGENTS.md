# Documentation authoring

Read `README.md` to choose an article, static demonstration, or interactive island and to run verification. Follow the repository-root `AGENTS.md`. The Docs authoring checks, TypeScript, ESLint, and nearby tests describe supported syntax, but they cannot judge factual accuracy, translation quality, or arbitrary function purity.

- Write for someone who lands directly on a guide: make the first useful action and route into the app clear, then answer the reader's questions. For a new guide or major restructure, settle the audience and section purposes before drafting and have another reviewer challenge that outline.
- Verify claims and illustrated behavior against current app source and tests. Preserve the meaning, safety boundaries, and link destinations of existing prose; keep claims of provenance or safety within the evidence.
- Docs replicas reproduce the app's presentation independently. Do not import app UI, stores, providers, permission handlers, or model runtimes. Use `components/demos/README.md` to find the current counterpart and preserve important visual and interaction details.
- Static pages and demonstrations produce complete, readable HTML in both development and production. They are not hydrated: `onMounted`, DOM access, watchers, and template event handlers cannot implement behavior there. Prefer CSS animation for an explanatory sequence; put new page-specific browser behavior such as input or API availability in a registered island. Keep the existing shared site controls in their own client entry rather than turning the page into a client application.
- Keep one article structure for both languages. Localize prose, visible UI labels, sample content, diagrams, captions, and accessible text naturally; use `UiLabel` for control names inside prose. Treat locale catalogs as read-only; rich message functions return fresh JSX or arrays rather than sharing mutable values across renders. Keep article messages on the server. Each island prepares only its selected locale's small messages; pass only required plain data through its typed JSON boundary.
- Use typed Docs link components for guide, app, local-anchor, and external destinations; keep external links visibly identified. Keep article IDs and public URLs stable when titles change.
- Motion should explain a step in a stable layout. Pause and reduced motion must leave a complete readable view and preserve reader selections. An animation must not trigger a model download, permission request, or command.
- Browser persistence belongs only to the existing theme and motion preferences in `client/preferences.ts`; do not create another storage path. Docs tests must not execute external commands or child processes, including through helpers.
- For Docs-only changes, follow the verification in `README.md`: use scoped ESLint fixes instead of repository-wide `lint:fix`, and run `test:only-failed` with the Docs config before committing.
